# Release process

Tarkov Companion publishes Linux x86_64 preview builds first. Windows and
mobile packaging stay deferred until the Linux artifact passes the manual
approval gate (design D9, task 9.6).

The release workflow is `.github/workflows/release-linux.yml`. It builds an
AppImage and checksums, optionally a `.deb`, generates release notes, and
uploads everything as a workflow artifact. A version tag additionally creates a
**draft** GitHub Release; a human publishes it.

Nothing in this process is signed. There are no signing keys, no secrets beyond
the automatic `GITHUB_TOKEN`, and no telemetry or third-party build service.

## Where the version comes from

`app/pubspec.yaml` is the only source:

```yaml
version: 0.1.0+1
```

- `0.1.0` is used in artifact names, the desktop entry, release notes, and the
  tag check.
- `+1` is the Flutter build number.
- `scripts/package-linux.sh` refuses a version that is not
  `MAJOR.MINOR.PATCH`.
- The release workflow refuses a tag whose name is not `v<version>`. Bump the
  pubspec before tagging; never retag around a mismatch.

## Triggers

| Trigger                                  | What happens                                         | Publishes? |
| ---------------------------------------- | ---------------------------------------------------- | ---------- |
| Actions → Release (Linux) → Run workflow | Builds, verifies, smoke-launches, uploads artifacts  | No         |
| Push a `v*.*.*` tag                      | The same build, then creates a draft GitHub Release  | Draft only |
| Pull request / push to `main`            | `.github/workflows/ci.yml` builds the package for CI | No         |

The release workflow is intentionally separate from `ci.yml`: a normal commit
must not be able to create a release, and a release run must not depend on the
test matrix.

## Manual dry run

Build and inspect the same files CI produces:

```bash
bash scripts/package-linux.sh
(cd dist && sha256sum -c SHA256SUMS)
bash scripts/release-notes.sh --checksums dist/SHA256SUMS --out dist/RELEASE_NOTES.md
```

`dist/` is ignored by Git. A dry run produces:

- `dist/TarkovCompanion-<version>-x86_64.AppImage` (about 12 MB)
- `dist/TarkovCompanion-<version>-x86_64.deb` when `dpkg-deb` is installed
- `dist/SHA256SUMS` in standard `sha256sum` format
- `dist/RELEASE_NOTES.md` with the checksum table and the signing statement

Pass `--tag v0.1.0` to validate the tag against the pubspec and `--commit SHA`
to record the commit. `--stdout` prints the notes without changing the file.

The notes generator does not tag, sign, upload, or call the network.

## Signing status

**The artifacts are unsigned.** No code-signing key, GPG key, or notarization is
configured. The release notes generated by `scripts/release-notes.sh` state this
on every release, together with the SHA-256 table.

Integrity evidence is therefore:

1. the published `SHA256SUMS` file, and
2. the workflow run linked from the release page, and
3. the source commit recorded in the notes.

If your environment requires signatures, build from source and compare the
result yourself. Do not add a signing key to this repository as part of an
unrelated change; a future signing design needs its own OpenSpec change.

## Approval gate

The workflow uploads artifacts but never publishes them silently in a way that
skips review:

1. A tag run creates a **draft** release with the AppImage, optional `.deb`,
   `SHA256SUMS`, and `RELEASE_NOTES.md`.
2. A maintainer downloads the draft assets and runs the checklist in
   [`linux-package.md`](linux-package.md): verify checksums, launch, first-run
   sync, search/filter/browse, restart offline.
3. Only after that checklist passes is the draft published and `v0.1.0` recorded
   in task 9.6.

Automated CI smoke-launches the AppImage under Xvfb and waits up to 25 seconds
for the process to stay alive. That proves the bundle starts and reaches the
Flutter engine; it does not prove sync or browsing work.

## Workflow permissions

- Top level: `contents: read`.
- `package` job: `contents: read`.
- `draft-release` job: `contents: write`, and only on a `v*` tag.
- No repository secrets are referenced. `GITHUB_TOKEN` is used to create the
  draft release.
- Actions are pinned to a major version (`checkout@v4`,
  `subosito/flutter-action@v2`, `upload-artifact@v4`,
  `download-artifact@v4`).

If the repository has a tag protection rule, the token still needs
`contents: write` to create the draft. Fork pull requests cannot run the release
workflow because it is not triggered by `pull_request`.

## Troubleshooting

| Symptom                                    | Cause                                     | Fix                                                                                |
| ------------------------------------------ | ----------------------------------------- | ---------------------------------------------------------------------------------- |
| `tag 'v0.1.1' does not match ... 'v0.1.0'` | Tag and `app/pubspec.yaml` disagree       | Bump the pubspec, commit, delete the un-pushed tag, retag                          |
| `flutter build linux --release failed`     | Missing GTK/CMake or a real compile error | Read the build log; reproduce locally with the same Flutter 3.50.1                 |
| AppImage smoke step exits 1                | Missing runtime library or an early crash | Check `dist/smoke.log` in the artifact; the AppRun wrapper keeps the bundle layout |
| `.deb` missing from the artifact           | `dpkg-deb` unavailable                    | Expected on non-Debian hosts; the AppImage is still a complete release             |
| `sha256sum -c` fails                       | Artifact changed after packaging          | Rebuild; never hand-edit `SHA256SUMS`                                              |
